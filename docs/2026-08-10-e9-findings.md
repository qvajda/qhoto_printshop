### New drift class found: pre-existing seasonal/holiday niches surfacing as bad copy

Four backlog candidates — **77** (`niche` suffix `holiday_peak`), **78**
(`diwali`), **79** (`black_friday_cyber_monday`), **81**
(`new_year_refresh`) — carried explicit seasonal-event niches straight into
their drafted copy ("for the holidays", "Diwali", "Black Friday Cyber Monday
Sale", "Welcome to the new year"), despite good underlying designs. A fifth,
**80** (`engagement_season`), was already rejected in an earlier session.

**This is not a GL-53 regression and not a live GL-47 failure.** All five
were created **2026-08-09T07:00:02 UTC — before GL-47 shipped** — and sat
stuck since the 2026-08-09 soak disabled the batch tasks. Today's re-enable
let them flow through generate → compliance_draft → critic_pass → digest for
the first time; GL-47's research-time gate was never in a position to catch
niches it predates. **Today's actual new research cycle (candidates 87-91)
produced zero seasonal niches** — GL-47 did its job correctly on live
research today.

That said, the underlying gap is real and independent of GL-47: neither
`compliance_draft`'s forbidden-term list nor `critic_pass` has any seasonal
awareness, so a seasonal niche — whether from a GL-47 gap, a future bug, or
simply re-surfaced backlog — reaches the owner's review queue as a full bad
draft on an otherwise good design. **Owner recommendation, GO-Live blocker
until resolved one way or the other:** either fix seasonal copy handling
properly (the niche's event context should inform tasteful copy, or be
filtered before it reaches drafting) so a seasonal niche never again
produces off-topic promotional insertions, **or**, if a proper fix isn't
ready by GO-Live, strip seasonal/holiday wording pipeline-wide as a stopgap.
A working proper fix relaxes this blocker on its own; stripping is the
fallback, not the goal.

## Operational findings (not scoped to claims a-d)

### 1. Telegram tap-drop reproduced live, first-hand

Taps for candidates 80/84/87/88(=80)/90's approve/reject decisions were made
with certainty by the owner and **vanished with zero server-side trace** — a
direct, no-offset query against Telegram's own `getUpdates` (bypassing this
app's stored cursor entirely) confirmed the bot's queue held nothing. Not an
offset-consumption bug in `publish_primary_group.py` (independently ruled
out). A re-tap of the same buttons minutes later landed cleanly with fresh
`update_id`s. This is a recurrence of the previously-flagged, never-fixed
tap-drop issue (candidates 57-60, flagged 2026-08-08) — happening at the
Telegram-delivery layer, outside this pipeline's own logging, so there is no
trace to investigate after the fact beyond "it happened, twice now, on two
different sessions."

### 2. Replicate 60s synchronous-wait produces false timeouts under batch bursts

Two pre-existing stuck candidates (78, 83) failed `generate` with "did not
complete within the 60s synchronous wait window," yet Replicate's own
dashboard showed both predictions **succeeded in 2.8s and 3.7s execution
time**. Not a contradiction: `replicate_client.py`'s own comment (lines
79-83) already flags that the 60s "Prefer: wait" window assumes near-zero
queue time. Firing 9 candidates' generate calls in quick succession against
an account capped at 6 req/min (no payment method on file — same file,
documented) plausibly queues jobs server-side long enough that the client's
60s window closes before the job even starts, while the job itself then runs
fast once its turn comes. The code's own suggested fix (switch to async
submit+poll instead of synchronous wait) already exists as a comment for
`upscale_image`'s cold-boot case; this run shows the same failure mode now
hitting `generate_image` (flux-schnell) too under burst load.

### 3. Anthropic `max_tokens=200` truncation on art-brief writer

Candidate 81 failed `generate` attempt 1 with "Anthropic response truncated
at max_tokens=200; raise the cap," succeeded on retry. Distinct root cause
from #2, unrelated to Replicate. Echoes a previously-fixed instance of the
same class (critic_pass's own cap raised 2048→4096) — this call site needs
the same treatment.

### 4. `SharedProductVariantError` treated as retryable when it's structurally permanent

`group_mockup` failed on candidates 1 and 39's 5x7 groups: their Gelato
products predate the v4.12 single-listing model, so `group_product.py`
correctly refuses to add a variant (GL-22a Q2 — no API path exists). But
`group_mockup.py`'s exception handler (lines 132-134) leaves the group at
`pending_generation`, explicitly commented "retryable next cycle." This
error can never succeed on retry, by construction — it will re-fire and
re-alert Telegram on **every future batch cycle indefinitely** until someone
manually marks these two groups `failed_abandoned`. Needs a special case:
`SharedProductVariantError` (and any other structurally-unrecoverable error)
should mark the group `failed_abandoned` immediately, not leave it retryable.

### 5. No copy-only redo path — blocks recovering the "good design, bad copy" backlog

Telegram's "✏️ Edit" button (`publish_primary_group.py:262-285`) does not
redo just the copy. It deletes `listing_texts`/`critic_pass_attempts` **and**
calls `generate.generate_for_candidate` with the edit note as a FLUX
correction_note — a full new image generation that can produce a visibly
different design. There is currently no way to keep a good design and only
redraft its copy. This run alone surfaced 4 such candidates (77, 78, 79, 81);
recovering that backlog (and the larger one referenced in owner feedback)
needs this path built first.

### 6. Etsy gallery/featured-image order has no code-level control

Confirmed in code: `etsy_client.upload_listing_image` (`pipeline/etsy_client.py:69`)
never sends a `rank` field to Etsy's API, on any upload call — despite
`group_product.py`'s `_GROUP_RANK_SQL` correctly computing "primary group
first, then 5x7, then 10x24" ordering for its own upload loop. Reproduced
2/2: both candidates that reached a published listing today (84, 87) show
the **10x24 mockup** (last group uploaded in the loop) as the Etsy listing's
featured/first gallery image, not a primary-group mockup. Root cause
confirmed as a missing parameter in the outbound API call; Etsy's own
resulting default-ordering behavior not independently verified against live
docs. Fix: pass `rank=1` on the primary group's first image.

### 7. Missing operational config knobs

No `.env`/settings control over:
- number of candidates generated per batch cycle,
- error-message verbosity in Telegram notifications,
- a research-mode toggle (always-research / off-consume-pending-only /
  on-if-nothing-pending) to separate "generate new candidates" from
  "just process pending approvals."

### 8. Scheduled-task runtime has no captured stdout/stderr

`qhoto-batch-morning`/`-evening`/`qhoto-hourly`'s Task Scheduler actions
redirect no output. Live progress during this run could only be inferred by
polling the DB/heartbeat/process list, never read directly. Worth adding log
redirection to the Task Scheduler actions (or a file handler in the scripts
themselves) for future operational visibility — this run spent significant
time guessing whether the batch process was working or hung before
confirming via CPU-time and DB polling.
