## §0. The problem, in one sentence

**Every stage after `generate` reasons about the artwork through a description of
it rather than through the artwork**, and E10 is where that finally cost
something: three good designs abandoned in one night, alt text discarded on every
listing ever published, and a gallery uploaded in an order nobody verified.

The proof is that the one stage which *does* receive the images — the critic —
was correct all night, three times over, about a mismatch the drafter was
structurally incapable of fixing.

**This is not four bugs. It is one missing channel with four symptoms.** Scoping
E11 around the channel rather than around the symptoms is the whole design of
this document, and it is why GL-68/69/70/71 belong in one session rather than
four.

---

## §1. Why this is the next thing, and not the activation

The shop is one owner action from its first buyer-visible listing: candidate 81's
listing `4554354628` is a complete, clean draft, and ticking "an AI generator" in
Etsy's web editor is the same save that activates it. Nothing external blocks it
— GL-11 can only improve on an answer GL-37 already settled.

**The reason to wait is an absence in Etsy's API, not a preference.** Alt text and
gallery rank are both set **at image-upload time**. Etsy v3 has no update-image
endpoint. Confirmed in code, not assumed: `etsy_client.upload_listing_image`
(`pipeline/etsy_client.py:69`) builds a multipart body carrying `image` and
`rank`, has **no `alt_text` parameter at all**, and `group_product.py:621` is its
only caller.

So the cost of fixing GL-69 and GL-71 is not a constant:

| When | What repair costs |
|---|---|
| **While 81 is a draft** | one re-upload nobody sees |
| **After activation** | new image ids and new URLs on a listing that has age, stats, and a permanently frozen URL (GL-41) |

**Owner decision 2026-08-12: hold the activation until GL-69 and GL-71 land.** A
few days of not being live, bought against a permanently degraded first listing.

**State this plainly so it is not re-derived later: the window is a state, not a
schedule.** It closes the instant the AI-generator box is ticked, and it cannot be
reopened cheaply.

## §2. E11a — the copy-integrity chain (GL-68, GL-70, GL-72)

### What is broken

`compliance_draft.build_draft_prompt` (`pipeline/compliance_draft.py:244`) passes
the model four things: the sanitised niche, `len(image_types)`, the joined
`image_types` (the literal strings `"flat"` / `"lifestyle"`), and
`MAX_TITLE_LENGTH`. Not the images. Not `candidate["art_brief"]`, which is on the
row the function already holds.

`critic_pass.run_critic_pass` then branches on `copy_only` in exactly two places
(lines 539 and 556). **The rubric is untouched**, `run_local_and_master_gate`
(line 520) still grades the image file, and line 547 still reaches
`abandon_candidate`. And in **both** modes, `build_compliance_draft` (line 565)
receives no correction argument — `critic_pass_attempts.correction_notes` was
`NULL` on all 12 rows E10b wrote, so three retries were three identical blind
draws.

### The three fixes, cheapest first — and all three are smaller than the findings imply

1. **Show the drafter the artwork (GL-68).** `anthropic_client` already has
   `complete_with_images`, and `_image_content_block` already accepts a local
   path. `candidates.base_image_local_path` is the column `run_local_and_master_gate`
   itself reads five lines away. So the fix is a call swap plus a prompt clause,
   not new plumbing. **Pass `art_brief` in the same change** — it is free and it
   carries intent the image cannot.
2. **Feed the critic's reason back (GL-70, half one).** `generate_draft_text`
   *already* takes `retry_feedback` and appends it to the prompt. The gap is
   purely that `build_compliance_draft` has no parameter to forward. Thread one
   argument through and persist it to `critic_pass_attempts.correction_notes` so
   the next triage can see it. **Ship this even if everything else slips** — the
   normal path has the same gap, merely masked because regeneration does receive
   the note.
3. **Stop `copy_only` being graded on, and abandoning for, what it cannot change
   (GL-70, halves two and three).** Skip `run_local_and_master_gate` in
   `copy_only` mode; narrow the rubric to copy/art *agreement* rather than art
   *quality*; and on exhausting the budget **hand the group back to the owner
   rather than calling `abandon_candidate`** — the owner has just said they want
   to keep this design, which is the same reasoning that made `redraft` reset the
   retry budget (PRD 2026-08-10 §6.3).
4. **Clear `failed_reason` on the success path (GL-72).** One `UPDATE`. Candidate
   81 is `completed` and still carries a `max_tokens=200` error from a cap GL-60
   deleted.

### The test that has to exist, not just the fix

Per the GL-53 lesson and its two recurrences (see §6): **an assertion in code, not
a sentence in a prompt.** At minimum — a test that `build_draft_prompt`'s output
contains the art brief and that the drafting call is the image-carrying one; a
test that `copy_only` never calls `run_local_and_master_gate`; a test that
`copy_only` cannot reach `abandon_candidate`; a test that a non-null correction
note reaches the draft call. **Assert the call that is made, not a mock of
whichever call the code happens to pick** — four tests passed against E10c's
broken reconcile endpoint for exactly that reason (§10).

### Success criteria

- A drafting run on candidate 77's intact artwork produces copy the critic passes
  **on the first attempt**, with no change to the artwork (sha256 unchanged
  against `6a972e41…4972c`).
- `critic_pass_attempts.correction_notes` is non-null on any attempt after the
  first.
- `copy_only=True` cannot mark a candidate `failed` by any path.

## §3. E11b — the gallery-integrity pair (GL-69, GL-71)

**This part measures before it fixes.** Both rows have a plausible fix that would
look like it worked and might not be the fix.

### GL-69, alt text — one measurement, then one form field

**Step 1, non-negotiable:** confirm `alt_text` is an accepted multipart field on
`uploadListingImage` by uploading one image to a throwaway draft and **reading it
back**. Do not take the documentation's word for it. This project's own
convention is *verify by measurement, not by status code*, and GL-22a Q2 is the
row that earned it — Gelato returned `200` for a change it silently dropped.

**Step 2:** add the field to `upload_listing_image`, read `product_images.alt_text`
at the call site, and fail loudly rather than silently uploading an empty string
when a row has no alt text.

**Step 3, the second half:** the secondary-group path (group 100) generates no alt
text at all. `update_gallery_alt_text` covers the primary gallery only. Both halves
or the defect only shrinks.

**Also delete or correct the false docstring** in `check_forbidden_terms` claiming
alt texts "go live on the listing". Leaving a comment that asserts a behaviour
which does not exist is how this survived a review that *added validation to it*.

### GL-71, gallery order — two hypotheses, discriminate first

| | Hypothesis | Test |
|---|---|---|
| **A** | The four duplicate `approve:100` taps raced the uploads (three image ids come from a later id family) | Re-upload 81's gallery with a **single** dispatch and see whether the permutation recurs |
| **B** | We upload our ranked images **before** reconciling away Gelato's seeded previews, so Etsy inserts-and-shifts around images still present, and the later deletions leave a permutation | Read the listing's images **between** the upload loop and the reconcile — if Gelato's seeds are interleaved at that moment, B is confirmed without a new create |

**B is testable on 81 today with no live create, so test B first.** If B holds, the
fix is to reconcile *before* uploading — which the existing code comment rejects
because it "would leave the listing briefly imageless". **That reason does not
apply to a draft**, and every listing this pipeline builds is a draft at that
point. If B does not hold, A stands, and A has a consequence beyond this row
(§7).

**Do not fix both at once.** If you change the ordering *and* deduplicate the
dispatch in one commit, the next permutation tells you nothing.

### Success criteria

- Live read-back of listing `4554354628`: every image carries the alt text its
  `product_images` row holds, and live rank order equals DB `gallery_order`,
  flats before lifestyles.
- The cause of the permutation is **named with evidence** in the findings doc, not
  inferred from the fix having worked.

## §4. E11c — the GL-75 restore (candidates 77, 78, 79)

**Strictly after E11a merges. Not before, for a stated reason:** redrafting them
now walks into the identical wall and spends Anthropic tokens doing it.

- Artwork is byte-identical and verified against sha256 taken *before* E10b:
  77 `6a972e41…4972c`, 78 `841fe7d3…7ddc3`, 79 `fb656b41…b148c`. **Re-verify
  after the restore, not before** — a hash checked only at the start proves
  nothing about the end.
- Backup exists: `db/qhoto.sqlite3.bak-2026-08-11-pre-e10b`. **Take a fresh one
  before the restore anyway**; the E10b backup is now two nights and one live
  publish stale.
- Restore path: targeted status reset on the candidate and its primary group, then
  `handle_decision(conn, candidate_id, group_id, "redraft", …)` — **not** a
  digest re-send, because `run_digest_cycle` excludes groups that already hold a
  `group_messages` row, and `handle_decision` clears it itself. This is the
  prerequisite the E10 kickoff had to discover the hard way; it is written here so
  the next session does not rediscover it.
- **Delete `scripts/e10b_backlog_recovery.py` once this completes.** It is
  throwaway by declaration and it is the kind of script that becomes load-bearing
  by accident.

**Success criterion:** all three reach `primary_review` with a passing critic
verdict and unchanged artwork hashes.

the draft:

1. Owner reads back the draft listing — alt text present, gallery order

2. Owner opens the Etsy web listing editor, ticks **"an AI generator"** under
   *What tools are used to make this item?*, and saves. **That save activates the

   Etsy's design and not ours (GL-37).
3. Record the activation timestamp and the listing state in the findings doc. It
   is the shop's first live listing and the first data point on every post-launch
   row that has been waiting for one.

disclosure was removed from descriptions (`DISCLOSURE_TEXT = ""`) and that is only
safe because this tick happens. Do not automate activation (GL-29b stays parked)

## §7. Open decisions for the owner

1. **The GL-65 workaround may be GL-71's cause.** The quadruple `approve:100` tap
   ran `handle_decision` up to four times for one group. The idempotent Gelato
   create held under it — one product, one row, a better test than any planned one
   — but **the gallery was not proven safe under it**, and that is hypothesis A.
   **If E11b's measurement lands on A, "tap a lot" needs a guard** (dispatch
   dedupe on `update_id`, or a short-window lock on `handle_decision`), and GL-74
   gets more urgent at the same time. **Decision requested: accept that the guard
   comes into E11b's scope if and only if A is confirmed** — otherwise it is a
   speculative fix for a cause we did not measure.
2. **`RESEARCH_MODE=consume-pending-only` — keep it, with a written removal
   trigger.** It is still set in `.env`, the batch tasks are re-enabled, and the
   E10 kickoff's instruction to unset it was not carried out. **Leaving it is
   correct today**, for a reason the hand-off did not give: with GL-68 open,
   researching new candidates manufactures more copy/art mismatches to repair by
   hand. **Decision requested: unset it when GL-68 is merged *and* the GL-75
   backlog is drained — not on a date, and not before.** Recorded as a step in §8
   so it cannot rot into a leftover a second time.
3. **The batch tasks stay disabled until GL-68 merges.** The owner has already
   acted this way; this asks for it to be a recorded decision rather than a state
   of affairs. **Hourly stays on** at 60 minutes — decisions land, toasts do not,
   and that was measured, not argued (§5 of the findings). Do not re-litigate the
   cadence without new evidence.

## §9. Tool-fit flag (`CLAUDE.md` §7)

**This is a Claude Code session, not a Cowork one.** It is multi-file code with a
790-test suite, a live API measurement and a git branch — Cowork's sandbox is the
wrong shape for all four, and the planning/execution split this project already
runs is the right one. Nothing here argues for a third tool.

**One genuine hand-off candidate, named rather than gestured at:** the GL-71
discrimination in §3 is an *observation* task against a live listing — read the
gallery between two calls and look at what is there. If it turns out to need eyes
on Etsy's own editor rather than API output, that is Claude in Chrome against the
listing page, not a script. Cheap to try the API way first; say so in the findings
either way.
