## GL-47 — the "too early" gate and the duplicate sweep

**File:** `pipeline/research.py`. Two independent defects in two functions.

### Defect 1 — `_classify_by_timing` has a "too late" test and no "too early" one

```python
def _classify_by_timing(raw: dict, now: date) -> dict:
    days_until_close = (raw["window_end"] - now).days
    if days_until_close >= MIN_EVENT_LEAD_DAYS:      # 14
        return {"go_hold_kill": "go", ...}
```

The only question asked is "does the window close soon?". Nothing asks "does
the window *open* soon?", so every entry in `EVENT_WINDOWS_2026` classifies
`go` for essentially its whole preceding year. Measured against today
(2026-08-10), the state of the six windows is:

| Window | Opens | Closes | Days to open | Classifies today |
|---|---|---|---|---|
| `fall_cozy_aesthetic` | 2026-09-01 | 2026-10-31 | 22 | `go` — and correctly so |
| `holiday_peak` | 2026-11-10 | 2026-12-20 | 92 | `go` — too early |
| `diwali` | 2026-11-08 | 2026-11-08 | 90 | `go` — too early |
| `black_friday_cyber_monday` | 2026-11-27 | 2026-11-30 | 109 | `go` — too early |
| `engagement_season` | 2026-11-21 | 2027-02-14 | 103 | `go` — too early |
| `new_year_refresh` | 2027-01-01 | 2027-01-31 | 144 | `go` — too early |

That is 5 of 6 wrong, and it is why holiday and fall candidates were generating
in August. **The table above doubles as your test fixture** — freeze `now` at
2026-08-10 and assert exactly one `go`.

**Fix shape:** a second predicate — `go` only when the window opens within
`MAX_EVENT_LEAD_DAYS` — with `hold` and a `hold_recheck_date` otherwise, reusing
the existing hold machinery rather than inventing a new state.

**Pick the constant deliberately and write the reasoning in a comment beside
it.** The pipeline's own latency is the input: research → generate → primary
critic pass → owner review → secondary groups → owner review → publish is a
multi-day loop on a twice-daily cadence, and Etsy listings need runway to
accumulate views before a window opens. **A defensible default is 45 days**,
which keeps `fall_cozy_aesthetic` live today and holds the other five. Do not
just pick 14 for symmetry with `MIN_EVENT_LEAD_DAYS`; the two numbers answer
different questions. If you disagree with 45, say so with the reasoning — this
is a judgement, not a spec.

**One edge case to handle explicitly:** `engagement_season` runs
2026-11-21 → 2027-02-14, so a window can be long enough that the two predicates
must be evaluated independently rather than as one range test. And a window
that is *currently open* must stay `go` regardless of the lead-time rule —
`days_until_open` will be negative, and the obvious `abs()` bug turns an open
window into a rejected one.

### Defect 2 — `collect_event_lookahead` returns the same six every call

```python
def collect_event_lookahead() -> list:
    return [ ... for window in EVENT_WINDOWS_2026 ]
```

No connection argument, no check against existing candidates. Two batch runs
close together produce near-duplicate candidates across all six event niches —
observed during the soak.

**Fix shape:** a dedup pass against non-terminal candidates for the same niche
(or the same `trend_source`, which is already `event_lookahead:<name>` and is a
cleaner key than the free-text niche string). Whether the filter lives inside
`collect_event_lookahead` (which then takes a `conn`) or in its caller is your
call — **state which you chose and why**, because it changes whether the
function stays pure.

**Compounding, and the reason both halves are one item:** these two together
regenerate the same premature niches every batch, burning Replicate and
Anthropic spend, and under live mode they reach real listings.

- a currently-open window still classifies `go`;
- a window inside the lead-time band but past `MIN_EVENT_LEAD_DAYS` of its

- a second `collect_event_lookahead` call with an existing non-terminal

## GL-46 — a swallowed per-candidate failure must leave a state change behind

**File:** `pipeline/generate.py`, `run_generate_cycle`, lines ~256–264:

```python
        try:
            result = generate_for_candidate(...)
        except Exception as exc:
            print(f"generate_for_candidate failed for candidate {candidate_id}: {exc}")
            continue
```

The candidate's status is never set. Because the exception dies here it never
reaches `run_batch.py`'s `_run_stage` outer catch either, **so no Telegram
notification fires and the row is indistinguishable from "hasn't run yet"**.

**The evidence that this is systemic, not flaky:** 2026-08-08, candidate 45
stuck `pending`, generated cleanly on a manual retry with no code change;
2026-08-09, **8 of 8** new `go` candidates (76–81, 83, 84) stuck at `pending`,
zero reached `generate`, candidate 76 reproduced by hand. Plausible but
unconfirmed cause: `generate.py`'s own Replicate rate-cap pacing tripping across
an unusually large queue. **You are not being asked to fix that cause** — you
are being asked to make it impossible for the next one to be invisible.

**Why the current behaviour is worse than it looks.** Transient failures
self-heal for free, because the next run re-queries `WHERE status = 'pending'`.
That is exactly what makes it dangerous: it looks benign right up until a
persistent failure (bad prompt, expired token, real outage) parks a candidate
forever. And the self-healing is slower than it sounds — `generate` runs on the
batch cadence only, so a fully-stuck batch waits 12 hours, which under live
mode is real delay on dated seasonal content.

**Fix shape, deliberately small:**

1. On the exception, record the failure on the row — a `failed` status carrying
   the reason, so the row stops being indistinguishable from unstarted.
2. Let it reach `_run_stage` so the **existing** Telegram surfacing fires. Do
   not build a second notification channel; GL-7 already has one.
3. Add a **retry counter** so a genuinely transient failure still self-heals
   instead of being condemned on first error. Check whether
   `generation_attempts` (there is a `migrate_generation_attempts_table.py`)
   already gives you this before adding a column — reuse beats a new field.

**The tension to resolve explicitly, because it is the whole design question:**
requirement 2 (propagate so the stage reports) and requirement 3 (keep going so
one bad candidate does not strand nine good ones) pull against each other. The
likely resolution is *continue the loop, accumulate the failures, raise once at
the end* — but decide it, do not stumble into it, and write the choice in a
comment.

**Two things already checked for you, so you do not spend the session on
them.** (1) **No migration is needed.** `candidates.status`'s CHECK already
admits `'failed'` (`'pending','generating','primary_review','compliance_failed','failed','abandoned','completed'`)
and the table already carries a `failed_reason` column. Use both; do not add a
column. The DB is at `schema_version` 8 and should stay there. (2) **Check what
reads `failed` before you write it** — a status nothing sweeps is half a fix,
and `reconcile.py` is where an age-out or recovery pass would already live if
one exists. If nothing reads it, say so rather than building a sweep on
spec — that is a separate decision with GL-36's shape.

### GL-46 done when

- a per-candidate exception leaves a `failed` row with a reason, and the
  remaining candidates in the batch still run;
- the failure reaches `_run_stage` and the existing Telegram path is invoked
  (assert on the mock; send nothing);
- a candidate under the retry threshold is re-attempted on the next cycle;
  over it, it is not;
- no schema change is expected (see above). If one turns out to be needed
  anyway, it ships as a numbered, additive, idempotent migration wired into
  `migrate.py`'s `MIGRATIONS` chain — **not** as another orphan `migrate_*.py`
  at the repo root. That was GL-35's whole finding.
