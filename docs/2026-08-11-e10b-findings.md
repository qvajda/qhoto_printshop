## §1. Root cause, traced in code

Three defects in a chain. None of them is the symptom the run showed.

### (a) The drafter never sees the artwork

`compliance_draft.build_draft_prompt` (`pipeline/compliance_draft.py:244`) passes
the model exactly four things:

```python
DRAFT_TEXT_PROMPT_TEMPLATE.format(
    niche=sanitize_niche(candidate["niche"]),
    image_count=len(image_types),
    image_types=", ".join(image_types),
    max_title_length=MAX_TITLE_LENGTH,
)
```

Not the images. Not even `candidate["art_brief"]`, which is in the row it already
holds. `image_types` is a list of the strings `"flat"` / `"lifestyle"`, not
content. **The listing copy is invented from a four-word niche and has no channel
through which the actual design could inform it.** On a candidate whose art
happens to match the niche this is invisible; that is why it has never surfaced
before.

### (b) GL-55's sanitisation makes (a) actively wrong for event-derived art

These four candidates' artwork was generated from event-laden niches. The
sanitiser correctly strips the event before drafting — and the art was generated
*before* the sanitiser existed, from the unstripped string:

| Candidate | Art was generated from | Drafter now told | What the images actually show |
|---|---|---|---|
| 77 | `… - holiday_peak` | `botanical/minimalist nature illustration peak` | red cardinal on pine branches, red berries, orange sun disc |
| 78 | `… - diwali` | `botanical/minimalist nature illustration` | (Diwali-derived scene) |
| 79 | `… - black_friday_cyber_monday` | `botanical/minimalist nature illustration` | — |
| 81 | `… - new_year_refresh` | `botanical/minimalist nature illustration refresh` | minimalist stem, faint arch |

So the drafter writes truthful-sounding minimalist-sage-leaf copy, and the critic
— which **does** receive the images — correctly rejects the mismatch. Verbatim,
attempt 3 on group 87:

> Severe mismatch: the title/description promise a minimalist single line-drawn
> leaf in a muted neutral/sage palette, but every image actually shows a detailed,
> colorful illustration of a red cardinal on pine branches with red berries and an
> orange sun — wrong subject, wrong medium (filled illustration vs. line art), and
> wrong palette entirely.

**The critic is right and the drafter cannot possibly satisfy it.** 81 passed only
because `new_year_refresh` art happens to look like generic minimalist botanical
work; it is luck, not correctness. Note this is not an argument against GL-55 —
the sanitiser is doing its job. It is an argument that (a) has to be fixed for
GL-55 to be safe on pre-GL-55 artwork.

### (c) `copy_only=True` narrows nothing that matters, and retries blind

`critic_pass.run_critic_pass` (`pipeline/critic_pass.py:491`) branches on
`copy_only` in exactly two places — line 539 (skip
`discard_superseded_attempt`) and line 556 (skip `generate_for_candidate` +
`create_primary_mockup`). **The rubric is untouched.** So a copy-only retry is
still graded on artwork composition, which it is structurally forbidden to
change, and still hits `abandon_candidate` at line 547–550. Verbatim, group 87
attempt 2:

> The orange orb behind the cardinal is a floating backdrop shape not clearly
> integrated with the surrounding branch composition… multiple compositions show
> branches stopping short of the bottom/side edges leaving asymmetric blank bands.

Every word of that is about the artwork. No redraft of any title can address it.
`run_local_and_master_gate` (line 520) grades the image file too, and in
`copy_only` mode it is both wasted spend and a pure rejection source.

Compounding it: **the critic's reason is never fed back into the redraft.** In the
regeneration path, `generate_for_candidate` receives
`correction_note=result["reason"]` (line 558). `build_compliance_draft` (line 565)
receives **no correction argument at all, in either mode** — and
`critic_pass_attempts.correction_notes` is `NULL` on all 12 rows this run wrote.
So each of the three attempts redrafted from the identical four-word prompt and
reproduced the identical mismatch. **The retry budget was spent three times on
the same blind draw.** This half is not specific to `copy_only`; the normal path
has the same gap, it is just masked there because regeneration does receive the
note.

## §2. What follows

- **(a) is the fix that matters.** The drafter should see the design — the
  artwork itself, or at minimum `art_brief`, which is already on the row it
  reads. Everything else is downstream of copy that describes an idea of the
  design rather than the design.
- **(c) has two independent halves.** `copy_only` must not be judged on, or
  abandoned for, defects it cannot fix; and the critic's reason must reach
  `build_compliance_draft`. The second half is worth doing even if the first is
  deferred, because it affects the normal path too.
- **An owner-initiated copy redo arguably should not be able to abandon the
  candidate at all.** The owner chose to keep that design. Running out of copy
  attempts is a reason to hand it back to the owner, not to mark it `failed` —
  the same reasoning that made `redraft` reset the retry budget in the first
  place (PRD 2026-08-10 §6.3).
- **77/78/79 are recoverable and should not be retried before (a) lands.** The
  artwork is intact, the pre-run backup exists, and a targeted status restore is
  cheap. Redrafting them again first would walk into the same wall and spend
  Anthropic tokens doing it.

**Owner decision, 2026-08-11: proceed to E10c using candidate 81, fix these
after.** E10c needs one candidate and 81 is clean, so the critical path is not
blocked by any of this.

## §4. GL-65: the tap is lost BEFORE Telegram, not by our cursor or our cadence

The 5-minute cadence turned `logs/telegram_getupdates.log` into a dense enough
record to settle this, and the answer is not the one the instrumentation was
built to catch.

**The measurement.** Owner tapped `✅ Approve` on message 430 at ~00:21. The poll
ran **90 times between 00:00 and 07:25 with no gap over 400 seconds** — every
run at offset `475586432`. Eighty-nine of those returned `{"result": []}`. The
ninetieth, at 07:25:01, returned `update_id 475586433` — **offset + 1, so it was
eligible for every one of the preceding 89 requests** — carrying `approve:94`.
Exactly one callback update existed in the whole window.

**The discriminating fact, which the log alone could not supply:** the owner
confirmed tapping message 430 **a second time at ~07:24**. `callback_query`
carries no tap timestamp, so this could not be read off the instrument — it had
to be asked.

**Therefore: the 00:21 tap never reached Telegram's queue.** The 07:25 update was
the re-tap. This rules out, with evidence rather than argument:

- **our offset/cursor handling** — the offset never moved off `475586432` across
  all 90 polls, so nothing consumed the update;
- **the poll cadence** — 89 polls in the window, so "we did not look" is dead;
- **machine sleep / the `Interactive only` logon mode** — the polls prove the box
  was awake and the task was firing;
- **a lost decision** — the re-tap dispatched cleanly and recorded `approved`.

**This corroborates E9's raw no-offset query** (which showed zero server-side
trace of taps the owner was certain of) from the opposite direction, and moves
GL-65 from "somewhere between the owner's thumb and our DB" to **client-side or
in transit, before Telegram's queue.** GL-45's row stays true — the path it
tested really is clean, because the loss is upstream of the path.

**What follows for the recommended next step:** the decision doc's item 1
(client-side capture on the owner's phone) is now the *only* item that can see
the failure, and item 2 (the ack) cannot — an ack cannot fire for a callback the
server never received. The ack change is still correct for the case where the tap
*does* land; it is simply not a GL-65 instrument. **A different confirmation
channel is the next decision point, exactly as the kickoff's "do not iterate"
clause anticipated.**

## §5. The ack expiry is confirmed, with one honest caveat

`logs/hourly.log` after the dispatch contains exactly one line:

```
answer_callback_query failed for 2122019755883058122: HTTP 400: {"ok":false,
"error_code":400,"description":"Bad Request: query is too old and response
timeout expired or query ID is invalid"}
```

So the kickoff §1 reasoning was right: the ack we already ship does fail against
a stale `callback_query_id`, and `_ack`'s docstring ("a lost spinner, not a lost
decision") describes real production behaviour. **The caveat: it expired across a
seven-hour delay, not across a five-minute one.** This run therefore does *not*
prove the 5-minute cadence delivers a toast — that needs a tap that reaches
Telegram and is collected on the next poll. Not yet observed.

## §6. `failed_reason` is never cleared on recovery

Candidate 81 reached `primary_review` with a passing critic verdict while still
carrying `failed_reason = 'gl46_generate_failed (attempt 1/3): Anthropic response
truncated at max_tokens=200; raise the cap'` — written 2026-08-10T16:09 on
generation attempt 1. Attempt 2 succeeded an hour later with a real FLUX
prediction (`qma2355z21rna0czxjh8xvrwhm`), and GL-60 has since removed that cap;
`grep` finds no `max_tokens=200` anywhere in `pipeline/`.

Nothing clears `failed_reason` when a candidate recovers, so a healthy row reads
as a failed one indefinitely. That is a trap for exactly the kind of triage this
session spent its first hour on, and it costs one `UPDATE` on the success path to
fix. Small, unfixed, filed.
