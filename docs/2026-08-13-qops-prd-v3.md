### 3.4 Opus 5 — the levers taken, and the softening refused

**Taken.**

- `effort` becomes an explicit knob in `.qops/config.yml` per agent role, with the
  guidance's own recommendation: start at `high`, use `low`/`medium` liberally
  where quality holds, reserve `xhigh` for demanding agentic work. This is the
  "policy file plus config knobs" the resumption assessment predicted for
  responsibility 2, and it is the only cost control the project actually has.
- A **delegation cap** in the plugin's orchestrator instructions, per the
  guidance: delegate only for large genuinely-independent tracks; one subagent
  rather than several.
- **Scope-fencing** language replaces verification-nagging in the agent
  definitions.
- A conciseness instruction plus a short end-of-prompt reminder, since verbosity
  is a prompting fix and not an `effort` side effect.

**Refused, and each refusal names the incident it would have missed** — the
kickoff's hard constraint.

The kickoff put three candidates. **The research found five, and rejected the one
the resumption assessment called "the single most consequential new fact".**

| Candidate | Real clock | Runs with the machine off | Real repo + credentials | Judgement | Verdict |
|---|---|---|---|---|---|

### 6.1 Why `SendMessage` is rejected, and it is not a preference

**It does not run on this owner's operating system.** Cross-session messaging is
available on macOS and Linux, including inside WSL 2; Anthropic's documentation
states plainly that Claude Code **does not offer it on native Windows**. This
project runs on Windows — the same fact `CLAUDE.md` already records twice, once as
"`.py` not `.sh`, for Windows/git-bash portability" and once as the Windows
scheduler that runs the pipeline's cron.

A second, independent confirmation from the other side: Desktop scheduled-task
sessions **cannot send or receive messages between desktop sessions** even where
the feature is available. So the runtime this PRD adopts for unattended per-project
work is a runtime `SendMessage` cannot reach, on a platform where it does not
exist. **The working hypothesis — "cron pass into each project's `.qops/`, plus
`SendMessage` for live cross-talk" — loses its second half entirely.**

Two escape hatches exist and neither is adopted now, because both cost something
real and nothing yet needs them: run Claude Code **inside WSL 2**, where messaging
works but the Windows-side pipeline host does not; or use **Remote Control**, which
routes cross-machine messages through Anthropic's servers and requires the
receiving session to be connected. **If the `qrchardist` ever genuinely needs live
cross-talk, WSL 2 is the cheaper of the two and it is a one-line trigger, not a
redesign.** Recorded so that a future session does not re-derive it.

**What replaces the rejected half.** Nothing live. Cross-project communication
becomes **asynchronous file hand-off**: a Routine writes into each project's
`.qops/`, and the next session in that project picks it up from the
`SessionStart` brief. Weaker than a channel, and honestly so — but durable,
platform-independent, and already the mechanism the brief exists to be. For
pushing *external* events into a session that is already alive — CI results, a
Telegram message — **Channels** is the right tool and is adopted for the
interactor (§5 B13), not for `qrchardist` cross-talk.

### 6.2 The three riders, and what each is worth now

- **Responsibility 1 is not orchestration — `qops init` ships first.** Unchanged,
  and it is Phase 7's portability proof under another name. Cheapest of the four,
  needs no orchestrator.
- **Responsibility 2 needs a measurement before a mechanism.** Unchanged, and now
  it has a first instrument that costs nothing: §5 E3's manual S1/S2 week, then
  `qops metrics`. The control surface remains coarse — cron cadence, model choice,
  **`effort`** — which is a policy file plus config knobs, not a scheduler. §3.4
  makes `effort` an explicit per-role config key, which is the whole of
  responsibility 2's v1.
- **Responsibility 4 is promoted, and it is the only one whose runtime now
  exists.** Notion freshness is a read, a diff and a write on a schedule — a
  **Routine**, exactly. It is also what un-demotes S5.

### 6.3 Phase 8+ scope, stated so it is not re-argued

The `qrchardist` builds **after** quriculum exists, per O1 and the resumption
assessment's rider (b): build quriculum by copy, instrument the divergences,
extract the shared foundation on evidence. A shared "Etsy pipeline" foundation
derived from one instance is a guess at the seam, which is the GL-71 error class.
**v1 of the qrchardist records echo obligations; it does not satisfy them.** The
runtime decision above is what Phase 8 starts from; nothing else about it is
decided here.

  the decision; deleting first is a no-op because a live plugin recreates the
  directory.

test → same; a green run permits it.

**Phase 5 — qops tracks itself.** From here, qops's work lives as issues in the

**Rider on decision 36, because the choice is right and the default execution of
it is not.** The editable path is the more consistent choice for this project:
`CLAUDE.md`'s own rule is that an instruction nobody can verify is a preference,
and an auto-updating read-only bundle is a dependency you cannot diff. Taking
editable copies makes the skills pinnable, diffable and reviewable, which is what
the rest of the design demands of everything else.

**But `npx skills add` lets you choose which skills to take, and taking all 21 is
how this decision turns into the bloat v2 set out to escape.** So the decision is
recorded as: **take only the ten qops actually depends on** — `wayfinder`,
`to-spec`, `to-tickets`, `grill-me`, `grill-with-docs`, `domain-modeling`,
`code-review`, `tdd`, `triage`, `setup-matt-pocock-skills` — plus `loopy`.
Eleven files you own and can pin, not twenty-one you inherit. Anything else on
the list is installed later, individually, when something needs it. `npx skills
update` pulls upstream changes **as a diff you read**, which is the whole benefit
being bought.
