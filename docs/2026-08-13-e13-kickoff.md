## §6. The orchard runtime decision — taken here, built later

Per O1 the orchard is Phase 8+, but **its runtime decision is taken now**,
because responsibilities 2 and 3 (distribute resources; maintain cross-project
communication) only have value *between* sessions, and there is no persistent
runtime. Three non-equivalent candidates, and the answer is likely a
combination:

| Candidate | Real clock | Real repo access | Judgement |
|---|---|---|---|
| Cowork scheduled task | yes | weak | yes |
| GitHub Actions | yes | yes | no |
| `SendMessage` / `ListAgents` | no — fires only when a session is already alive | n/a | yes |

**Working hypothesis to test, not to adopt:** a cron-triggered pass that writes
into each project's `.qops/`, plus `SendMessage` for live cross-talk.

Three riders from the assessment that shape v1 of the orchard:

- **Responsibility 1 is not orchestration** — "launch a new project with its own
  qops" is a scaffold command, `qops init`. Cheapest of the four, needs no
  orchestrator, and it *is* PRD v2's Phase 7 portability proof under another
  name. **Ship it first.**
- **Responsibility 2 needs a measurement before a mechanism.** Cross-project
  token starvation is hypothetical at one active project, and nothing collects
  per-project consumption (cf. E3). The control surface is coarse — cron
  cadence, model choice, `effort`. That is a policy file plus config knobs, not
  a scheduler.
- **Responsibility 4 should be promoted, not minor.** Notion freshness is a
  read + diff + write, already a scheduled-task shape, and the only one of the
  four whose runtime exists today.
