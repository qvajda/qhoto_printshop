### Two riders picked up while running it

1. **`create_draft_listing` was the only Etsy call that bypassed
   `_call_with_refresh`**, so it was the only one that died on an expired access
   token instead of refreshing once and retrying. Fixed (`pipeline/etsy_client.py`).
   It is still `DELIBERATELY` not used by any pipeline stage — Gelato creates the
   listing — but it is the probe's entry point and would have been a live trap for
   any future hand-run.
2. **Etsy now rejects a physical draft with no `readiness_state_id`**
   (`400 "A readiness_state_id is required for physical listings."`). The value used
   (`1428762550751`) was read off live listing `4554354628`, not invented. Nothing in
   the pipeline creates listings, so this costs us nothing today — recorded so it is
   not re-derived.

## §3b — the cause: **hypothesis A, duplicate dispatch. Measured, not guessed.**

The PRD's prescribed instrument (read the images between the upload loop and the
reconcile) can only observe a *future* upload. The incident itself left a better
record, so it was read instead of re-staged — Etsy's own
`created_timestamp` per image, against `telegram_events_log`.

**Upload timeline** (created_timestamp, UTC, in intended-rank order — monotonic,
so the loop itself uploaded in the right order with the right ranks):

```
rank  1  8371325764  07:26:40      rank  7  8371326528  07:26:55
rank  2  8419206401  07:26:42      rank  8  8371326746  07:26:59
rank  3  8371326014  07:26:45      rank  9  8371326990  07:27:05
rank  4  8419206643  07:26:47      rank 10  8371327314  07:27:11
rank  5  8371326340  07:26:51      rank 11  8371327594  07:27:17
rank  6  8419206961  07:26:53      rank 12  8371327850  07:27:23
```

**Dispatch timeline** (`telegram_events_log` ids 68–71, all `accepted=1`,
`action_taken='approve'`):

```
07:25:01  approve:100
07:26:52  approve:100
07:26:56  approve:100
07:26:59  approve:100
```

Four accepted dispatches of the same decision. The 07:25:01 one owned the upload
loop; the other three started **inside it**.

**Why this is A and not B.** The permutation is confined to intended ranks 3–7,
uploaded 07:26:45–07:26:55 — the window the three duplicate dispatches overlap.
Ranks 1–2 (uploaded before 07:26:52) are correct, and ranks 8–12 (uploaded from
07:26:59 on) are correct. Hypothesis B — Etsy inserting-and-shifting around
Gelato's seeded previews — is present for the *whole* upload and would have
disturbed rank 1 and the tail as well. A cause that is only active during the
concurrency window is the concurrency.

**Fix shipped, one change per observable:**

- `process_update` gains a **dispatch guard**: a callback for a group whose
  `groups.decision` is already terminal is logged `discarded: group already
  <decision>`, acked, and never dispatched. `handle_decision` commits the decision
  before doing any work, so the row is the authority the second tap loses to. The
  keyboard edit was never a lock.
- **GL-74 travels with it** (PRD §3b, owner decision): `❌ Reject` now sends
  `confirm_reject:` and only swaps the keyboard; `reject:` is reachable solely from
  the confirm keyboard, and `↩️ Keep it` restores the original. Neither branch
  writes to the DB.
- **No reorder fix was written.** Under hypothesis A the ordering code is correct;
  it was raced, not wrong. The `reconcile-before-upload` change the PRD scoped for
  hypothesis B is **not** shipped, and the comment rejecting it stands.

Tests: `test_process_update_discards_a_second_tap_on_an_already_decided_group`,
`test_process_update_reject_asks_for_confirmation_before_deciding_anything`,
`test_process_update_keep_restores_the_digest_keyboard_and_decides_nothing`.
