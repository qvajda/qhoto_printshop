## 1. Problem

GL-13 passed and proved the v4.12 publish path. Two things it surfaced are
wrong, and both are wrong *in the direction of the buyer*:

**GL-33 — the gallery is contaminated.** Gelato's product-creation push
creates the Etsy listing with its own preview images, one per variant (5 or 6
depending on how many groups passed). Our patch step then uploads the tracked
composites **alongside** them. The listing a shopper would see opens on
Gelato's generic renders, with the authored scenes somewhere behind them, in
an order nobody chose.

The whole GL-6/GL-21 mockup track — three failed authoring attempts, a
compositor unfreeze, a matte contract, a nine-detector QA gate — exists to
control exactly this surface. A contaminated gallery does not degrade that
work, it **voids** it. Two second-order costs: the 20-image cap is measured
against the contaminated total, so five or six ghosts also eat five or six
real slots; and `product_images` stops being a faithful description of the
listing, which is the assumption the idempotent re-patch rests on.

**GL-34 — much smaller than first filed. Read this before doing anything with
`who_made`.** The 2026-08-03 filing said `who_made: i_did` and
`production_partner_ids` are mutually exclusive, concluded a
mandatory-disclosure risk, and proposed moving to `someone_else`. **That was
wrong.** The owner produced a Shop Manager screenshot from the **GL-9 (v4.11)**
round showing, on one live listing, `Who made it? = I did` **and**
`Production partners for this listing: Gelato, Brussels, Belgium — Appears on
listing as "A print shop"`. They coexist.

So: no policy exposure, no disclosure decision, `CLAUDE.md`'s `i_did` line
**stands** (the §3 contradiction flag against it is withdrawn), and
`someone_else`/`collective` are **out of scope** — they would be *less*
accurate, since the design genuinely is the seller's, and would forfeit the
"designed by a seller" label for nothing.

**What remains is a diagnosis with a known-good control.** GL-9's patch sent
`production_partner_ids=[5717252]` alongside `who_made: i_did`
(`docs/2026-07-22-v411-live-test-launch-guide.md`) and the partner landed on
the listing. GL-13's patch appeared not to. Either the v4.12 patch path
regressed, or GL-13 read the **API response echo** rather than the listing's
actual state. One `GET` plus a dashboard look settles it.

**Blocking status:** GL-33 blocks GL-29 outright — activation is a one-way
door (`active` never returns to `draft`), so activating now publishes the
contaminated gallery with only `inactive` as a remedy. GL-34 blocks it only
in the weak sense of "confirm the field is there before you go live". GL-33
is also cheapest to fix *right now*, while every listing is a draft nobody is
looking at.

**Explicitly not in this session: GL-37.** The same screenshot showed
Etsy's Creativity Standards fields blank — "How does your shop produce this
item?" and "What tools are used to make this item?", the latter being where
**"An AI generator"** lives. That is owner-manual plus a research question
about whether the v3 API has since exposed either field, and it carries a real
consequence for GL-7's unattended premise. It is tracked separately and does
not belong in a coding session.

## 2. Success criteria

1. A live listing built by the pipeline carries **only** images this repo
   uploaded, in the rank order `patch_etsy_listing` chose, verified by a `GET`
   against Etsy — not against our DB.
2. That property survives a **second** patch of the same listing (the
   idempotency guarantee GL-13 R4 proved for uploads now has to hold for
   deletes too: no re-deleting, no re-uploading, no drift).
3. Deleting Gelato's images does **not** sever the Gelato↔Etsy sync or break
   the variant mapping — measured, not assumed.
4. After a patch, the production partner is present **on the listing** —
   confirmed both by `GET` and in Shop Manager, because those are two
   different sources of truth and this item exists because they were
   conflated. `who_made` stays `i_did`.
5. If a real regression is found, it is fixed and pinned by a test. If the
   GL-13 observation turns out to have been a response-echo artifact, that is
   written down as the answer and GL-34 closes — **"no defect" is a valid
   outcome here and does not need a code change to justify the session.**
6. The AI disclosure sentence in the description text is untouched.
7. Suite green, and green **including** new tests for GL-33's behaviour.

## 4. Constraints

- **Live writes only where §5 says so.** Everything else runs dry-run.
  CLAUDE.md §4: the destructive calls here are `delete_listing_image` against a
  real listing — show the plan, flag it, wait for an explicit "proceed".
- **Reuse the existing listing from GL-13 R3** rather than publishing a new
  candidate. It is a draft, it carries the contamination, and it costs nothing.
- **Do not delete an image we cannot account for as Gelato's.** The rule is
  positive, not negative: delete an Etsy image **only** if its
  `listing_image_id` is absent from `product_images.etsy_listing_image_id` for
  this `group_product_id`. Anything ambiguous stops the run and reports.
- **`who_made` and `production_partner_ids` are snapshotted per candidate at
  compliance-draft time** (`compliance_draft.py` writes them into the listing
  row; `patch_etsy_listing` reads `listing_text["who_made"]`, not
  `static_config`). **This is now a diagnostic fact, not a change to make:**
  if P3 finds the partner genuinely missing, the snapshot is the first place
  to look — a stale or malformed `listing_texts` row would produce exactly the
  observed symptom without any API misbehaviour at all, and would explain why
  GL-9 and GL-13 differ. Nothing here gets rewritten to change `who_made`.
- Subagent briefs carry the standing **command denylist** (Session R): no
  `git stash`, `reset --hard`, `checkout -- .`, `restore`, `clean`, `rebase`,
  `merge`, `cherry-pick`, history rewrite, `stash drop/clear`, `rm -rf` outside
  scratch, and no `*_LIVE_MODE` env var. Reading git state is unrestricted.

## 5. Plan

Ordered no-spend-first, exactly as GL-13's guide was.

### P0 — Read before touching (no writes)

`GET` the GL-13 R3 listing's images. Record: how many, their
`listing_image_id`s, their `rank`, and which of them match
`product_images.etsy_listing_image_id`. **This is the ground truth the whole
reconcile step is built on — build the parser around what comes back, not
around what the docs imply.** Confirm the count matches the "5 or 6, one per
variant" hypothesis; if it does not, stop and re-scope, because the mechanism
is then not what we think it is.

### P1 — The two client calls (offline, tested)

`get_listing_images(shop_id, listing_id, …)` and
`delete_listing_image(shop_id, listing_id, listing_image_id, …)`. Dry-run
returns a stub, live path goes through `_call_with_refresh`. Unit tests with a
faked `http.send`. **Mechanical and fully specified → Sonnet subagent.**

### P2 — The reconcile step (main thread — this is the risky one)

In `patch_etsy_listing`, **after** the upload loop and **before**
`update_listing`:

1. `GET` the listing's current images.
2. Build the set of `etsy_listing_image_id`s this candidate owns, from
   `product_images` scoped by `group_product_id` — the same scoping discipline
   `_INCLUDED_GROUP_SQL` already uses. **A wrong scope here deletes another
   group's reviewed gallery**, which is the identical failure class session 2
   guarded against; treat it with the same suspicion.
3. Delete every listing image whose id is not in that set.
4. Log each deletion with the listing id and image id, loudly.

**Order matters and is not arbitrary.** Uploading first and deleting second
means the listing is never momentarily empty, and our images inherit the low
ranks as Gelato's are removed. Deleting first would open a zero-image window on
a listing Etsy may refuse to leave imageless.

**Idempotency:** a second call finds nothing foreign and deletes nothing. Test
that explicitly — "runs twice, same end state" — because that is the property
GL-13 R4 bought for uploads and this step is the thing most likely to spend it.

**Deviation trigger:** if honouring "delete only what we can positively
account for" collides with anything else here, **stop and flag it**. Do not
route around it with a heuristic on filename, size or rank.

### P3 — The GL-34 diagnosis (live, read-mostly, ~30 minutes)

**Do not change `who_made`.** This is four observations, in order:

1. **The control.** `GET` the GL-9 (v4.11) listing from the screenshot.
   Confirm the API reports the partner that Shop Manager shows. If the API
   says *absent* on a listing the dashboard says *present*, the answer is
   already in hand — the response is not listing state — and steps 2–4 are a
   formality.
2. **The subject.** `GET` the GL-13 R3 listing. Partner present or absent?
3. **Compare the surfaces.** For whichever listing disagrees, look at Shop
   Manager directly. `GET` and dashboard are two sources of truth and this
   item exists because they were treated as one.
4. **If and only if the partner is genuinely absent on the listing:** re-patch
   with the current code, watch the request body actually sent (not the config
   value — the field is snapshotted into `listing_texts` at compliance-draft
   time and read from there), and find where it is lost.

Record it in `docs/2026-08-04-gl34-findings.md`, one section per observation,
verbatim responses — GL-22a's format. **A finding of "no defect, the original
observation was a response echo" is a complete and successful outcome.** Say
so plainly if that is what it is; do not manufacture a fix.

### P4 — Fix only if P3 found one

If a real regression exists, fix it and pin it with a test asserting the
partner survives a patch. If not, close GL-34 in the plan doc with the
findings link and move on. **Either way, no `who_made` change and no
`CLAUDE.md` edit.**

### P5 — Live verification

One guarded pass over the GL-13 listing: patch, `GET`, confirm criteria 1–5.
Then a second patch, `GET` again, confirm nothing moved.
