## 2. The starting term list would have missed the defect it was written for

**This is the finding that mattered.** The shipped sentence in all 27
descriptions is:

> "This design was created using **AI image generation** from the seller's own
> prompts…"

Against the kickoff's starting list (`ai generated`, `ai-generated`, `ai art`,
`artificial intelligence`, `midjourney`, `dall-e`, `stable diffusion`,
`generated with ai`) that string matches **nothing**. "AI image generation" is
not "AI generated". A substring list built from the drift we had already
*named* would have shipped green tests and left 27 of 27 unfixed.

So the list carries a second, separate rule: `FORBIDDEN_WORDS`, currently just
`ai`, matched on word boundaries, case-insensitive.

**The judgement call the kickoff asked to be recorded rather than papered
over — same list for all three fields, and here is why the feared false
positives do not exist.** A bare `\bai\b` cannot match inside `air`, `detail`,
`paint`, `mosaic` or `chair`: the word boundary is doing the work that a
narrower description-only list was proposed to do. A standalone `ai` token in
English art copy is always the acronym. The digital-product terms are safe on a
description for the same reason they are needed there — an honest description of
a shipped poster has no use for the word `printable`. Verdict: **one list, three
fields, no split.** If a legitimate description ever does trip it, the cost is
one regeneration, and the fix is to narrow one entry, not to split the list.

Two terms were added beyond the kickoff's list: `production partner` and
`gelato`. The same GL-37 decision covers them (Gelato is disclosed through
`production_partner_ids`), the prompt already forbade them, and 27 of 27
descriptions ended with *"Printed and shipped by our production partner,
Gelato."* — a fourth drift class hiding in the same sentence block as (a).

## 4. Yes: `compliance_draft` had the GL-46 shape, and it is fixed here

The kickoff asked. It did, **half of it**. `build_compliance_draft` already
marked the row `compliance_failed` with a reason (requirement (a) of the
CLAUDE.md rule was satisfied), but `run_compliance_draft_cycle` caught, printed
and `continue`d — so the stage returned success and `run_batch`'s `_run_stage`
never fired its Telegram notification. Requirement (b) was missing.

Fixed the same way GL-46 fixed `generate`: collect, finish the loop, raise
`ComplianceDraftCycleError` once at the end with every failure named. **No
re-queue**, unlike GL-46: a `compliance_failed` row is terminal at this stage
(an existing test pins that) and the retry budget already lives inside
`build_compliance_draft`'s three attempts. Two existing cycle tests had to be
updated to expect the raise — worth noting, because tests that asserted the
swallow were part of what kept it in place.

**That is a second instance of a rule written down four hours earlier.** The
honest read: GL-46's fix was applied to the stage where the failure was
observed, not to the shape. Four other stages (`primary_mockup`, `critic_pass`,
`digest`, the two `publish_*` cycles) have the same loop and were **not**
audited in this session — out of scope, and the *only* reason this one was
caught is that a kickoff document explicitly said "check whether". Worth a
ten-minute sweep of its own.
