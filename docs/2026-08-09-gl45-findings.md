## 2. The gap evidence does not prove what the brief said it proves

**This is the correction that matters, and it should be carried into any
re-reading of the brief's §0.**

The brief inferred, from 19 `update_id`s that exist in the sequence but have no
`telegram_events_log` row, that "something consumed them". That inference
requires every update the pipeline sees to produce a row. **It did not.**
`process_update` returned a silent, unlogged `None` for any update with no
`callback_query` — an ordinary message to the bot, a `/command`, anything.
Those updates consumed an `update_id`, advanced the offset, and left no trace.

So each gap had two explanations, not one, and the DB could not tell them
apart. Independently: gaps of the same shape exist on **2026-07-22** and
**2026-08-03/04**, well before any of the reported drop windows —

## 4. What *is* proven: the hazard is real, and it fired today

The canonical DB's last heartbeat is `hourly 2026-08-09T15:00:01`. Task
Scheduler reports `qhoto-hourly` last ran **2026-08-09 17:00, exit 0**. Two
successful hourly runs (16:00, 17:00) therefore polled Telegram — consuming
from the single server-side cursor — and wrote their results into the
**worktree** database, which GL-38 Phase D then deleted along with the
worktree. That is exactly the failure mode the brief describes, executed for
real, with the evidence removed a few hours later. It also explains
`pending_update_count: 0` without needing any tap to have been dropped.

It does **not** explain the 08-09 *morning* taps: for those, the hourly ran
against the then-canonical worktree DB, and its offset (`475586404`) and last
logged row (08-08 19:30) show those polls returned nothing at all. That window
remains unexplained, and is what the live reproduction in §7 has to catch.

## 6. What shipped

1. **Canonical-database guard** (`pipeline/db.assert_canonical`, migration 8
   `db_identity`). The DB records the absolute path it lives at; a copy carries
   the original's path and is therefore detectable. `run_publish_primary_group_cycle`
   — the single point that consumes the cursor, and the one all three
   entrypoints route through — refuses to poll from a non-canonical file.
   Deliberate promote-and-swap: `python migrate.py <db> --bless`. Escape hatch
   for offline work: `QHOTO_ALLOW_NONCANONICAL_DB=true`.
   **Applied to the live DB this session**, backup at
   `db/qhoto.sqlite3.bak-2026-08-09-pre-gl45`.
2. **Token-scoped lock** (`pipeline/lock.token_lock_path`). Both entrypoints now
   lock on `sha256(bot_token)` in the system temp directory instead of
   `<tree>/db/gl7.lock`, so every process using that token serialises against
   every other — "one token, any number of processes", not "one token, two
   trees". The token is hashed, never written to the filesystem.
3. **Explicit `allowed_updates`** on every `getUpdates` call.
4. **Raw-response instrumentation**: every poll appends one JSON line
   (timestamp, pid, cwd, offset sent, verbatim response) to
   `logs/telegram_getupdates.log` — a file, not the DB, so a DB failure cannot
   hide it. Git-ignored.
5. **Non-callback updates are logged** (§2).
6. **Tap acknowledgement** (brief §5): `answerCallbackQuery` now fires
   *before* `handle_decision` rather than after — a decision that spends
   minutes in Gelato/Etsy used to answer a callback query that had already
   expired, which is precisely why a tap that landed still looked dropped.
   `editMessageReplyMarkup` then replaces the keyboard with a single
   `✅ Approved` / `✏️ Edit requested` / `🚫 Rejected` label, so the
   acknowledgement outlives the toast. A re-tap on that label (`noop:<id>`) is
   answered "Already decided" instead of raising. The two discard paths
   (non-admin, no matching `group_messages` row) are answered too — silence was
   previously indistinguishable from a drop.
7. **Per-update offset advance.** `set_telegram_offset` ran once after the
   loop, so a run killed mid-publish re-delivered everything it had already
   handled (ids `365`–`367` appear twice in the live log, ten minutes apart,
   the second time as `error: Gelato product …`). The offset now commits per
   update; a kill costs at most the update in flight.

**724 tests pass** (709 before; 15 added).

Side effect worth noting: `migrate.py` now parses flags separately from the
path argument, which closes **GL-50** (`migrate.py --check` used to treat
`--check` as a database filename, open an empty file called `--check`, and
raise a false stale-schema alarm).

## 7. What is still open

- **Root cause of the 08-09 morning window.** Not reproducible from stored
  evidence; the instrumentation is in place to catch the next occurrence. The
  live reproduction wants: enable **only** `qhoto-hourly`, send a digest, tap,
  then diff `logs/telegram_getupdates.log` against `telegram_events_log`. The
  raw log now discriminates "Telegram never sent it" from "we received it and
  lost it" in one read — the fork the whole investigation could not resolve.
- **`.env` is a token-bearer.** Any new checkout that copies it can consume the
  cursor. The guard stops it from *hiding* the consumption (it refuses to poll),
  but the operating rule stands: one tree, one database, one poller.
- The genuinely lost 08-09 taps are the **secondary** groups 76–81 and 84
  (`decision IS NULL`). Groups 53, 55 and 59 carry `decision='approved'` with
  `status='pending_review'`, which is the correct v4.12 intermediate state —
  those taps landed. Diagnose from `groups.decision`, never from the digest
  looking unchanged.
