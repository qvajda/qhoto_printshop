## §3 — the diagnostic, and why the brief's method could not work as written

The brief said: download each `productImages[].fileUrl` and measure its pixel
aspect. **That measurement is not available from the API.** Every entry in
`productImages[]` is a **1000×1000 square preview render** of the product on
paper — not the print file we submitted. Six images, six identical dimensions,
no information about the submitted file's aspect at all.

What *is* readable, and is where the defect actually lives, is the rectangle the
artwork occupies **on the paper inside that preview**. Measured on candidate 42
(`5e15c0b4-…`, Etsy `4549960823`, created 08-04 from the **old** template):

| Variant | Paper aspect in preview | Placed artwork aspect | Verdict |
|---|---|---|---|
| 8x12, A3, A2, A1 | 0.708 | **0.709** | fills — no letterbox |
| 5x7 | 0.725 | **0.725** | fills — no letterbox |
| 10x24 | **0.420** | **0.651** | **letterboxed: artwork placed at ~0.68, paper is 0.42** |

The placed artwork on the 10x24 variant sits at the *master's* ratio inside a
0.42 sheet — the signature of a transform authored for 0.684.

**Which file was submitted, decided by content rather than by shape.** The
warm-toned artwork (the orange arc) spans a different fraction of the frame in
the master than in the crop, and the two are far apart:

| Source | Warm-pixel horizontal span (fraction of frame) |
|---|---|
| `42.png` (master, 0.6842) | 0.175 → 0.815 (arc fully inside the frame) |
| `42_10x24_crop.png` (0.4166) | 0.000 → 0.998 (arc clipped at both edges) |
| **10x24 preview, placed region** | **0.024 → 0.983** |

The submitted file was the **cover crop**. `_image_url_for` did its job; Gelato
then fitted that crop into a placeholder transform built for an ordinary
portrait photograph and padded the difference in white.

**→ One bug. §6 (the reuse-branch suspect) is therefore not on the critical
path** — see "Still open" below; it is still a real weakness, just not this one.

**Method note worth keeping:** verification for this integration is
*measure the placed artwork rectangle inside the preview*, not *measure
`fileUrl`* and certainly not *read the status code*. Implemented as
`scripts/gelato_template_check.py <product_id>` so §7 and every later live
create can run it in one command.

## §5 — the dry-run gate (`pipeline/group_product.py`)

The crop URL was gated on `config.is_live_mode("GELATO")`, so a dry run
submitted `candidate["base_image_url"]` — the uncropped master. That is why two
soak nights could not have caught this class of defect: night 1 ran a different
program.

**Fixed by removing the gate outright rather than by swapping it for
`is_r2_configured()`, as the brief suggested.** The suggested version would
have regressed an existing live-shaped guarantee: with R2 absent,
`is_r2_configured()` falls back to the master, and
`test_real_create_fails_loud_for_secondary_group_when_r2_not_configured` exists
precisely to assert that a *live* call in that state fails loud instead of
silently shipping the uncropped file. Handing over the crop's `durable_url`
unconditionally preserves both properties, in the same branch for both modes:

- live + R2 → the R2 crop URL (unchanged behaviour);
- live, no R2 → a local path → `GelatoInvalidImageURLError`, fails loud (unchanged);
- **dry run + R2 → the R2 crop URL (the fix)**;
- dry run, no R2 → a local path, and `create_product_from_template` returns its
  dry-run stub before any URL guard, so nothing breaks.

Regression test: `test_dry_run_create_sends_the_same_hosted_print_crop_as_a_live_one`.
Confirmed to fail against the old gate (`'https://replicate.delivery/master.png'
!= 'https://cdn.example.com/base/1_10x24_crop.png'`) before the fix landed.

The standing principle is now in `CLAUDE.md`: **dry-run changes what a call
does, never which code path reaches it.**
